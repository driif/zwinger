# zwinger domain

**Shield**: the unit of isolation. One shield is one host folder, one microVM, its mounts and its network policy. The folder is mounted read-write at `/workspace` in the VM. Nothing else from the host is visible: no host env vars, no credentials, no host home.

**Mount**: an extra host folder that the user adds to a shield explicitly. It has an absolute guest path that does not overlap `/workspace`. It is read-only by default.

**Network policy**: egress is denied by default. The user adds allowed domains (the allow list); `*.example.com` allows subdomains. In allow-list mode DNS resolves only listed names. "Allow all" means the public internet only. The host machine, the LAN, loopback, link-local and cloud metadata addresses are blocked in every mode. Ingress is always denied. Mount and network changes apply on the next shield start.

**Session**: one interactive terminal inside a running shield's VM. Kinds: `shell` and `pi` (pi in a terminal). There are no host (unsandboxed) sessions.

**Agent**: an AI coding CLI that the Agents tab talks to in a running shield, with no terminal: pi (`pi --mode rpc`), Claude Code (one long-lived `claude -p` per chat, stream-json in and out) or Codex (one `codex exec --json` per turn; the next turn resumes the thread). A shield has at most one agent of each kind. It starts in the harness, else in `/workspace`. A shield stop ends all its agents. The permission prompts of Claude Code (`--dangerously-skip-permissions`, with `IS_SANDBOX=1` because the guest runs as root) and the approvals and sandbox of Codex (`--dangerously-bypass-approvals-and-sandbox`) are off. That is acceptable only because the agent runs inside the shield: the shield is the sandbox, with only its mounts, its allowed hosts and placeholders for its secrets. Claude Code gets `HOME=/opt/zwinger/state/claude` and Codex `CODEX_HOME=/opt/zwinger/state/codex`, so the host `~/.claude` and `~/.codex` are never visible. They authenticate only with secrets: `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, and `OPENAI_API_KEY` or `CODEX_API_KEY`. Each agent process (also pi's) runs in a small Node wrapper that puts it in its own process group, so an abort or a stop kills the tool processes that the agent started, not only the agent. A process that loses its chat (new chat, chat switch, model change) gets its stdin closed; the next process and the agent's end wait until it exits, and it is killed after 5 s.

**Runtime**: the program of an agent, mounted read-only below `/opt/zwinger`; the shield needs no registry access. zwinger bundles pi (`/opt/zwinger/pi`). Claude Code and Codex are not bundled: the user installs them once, for all shields. The host downloads a pinned npm package for the host arch (linux-arm64 or linux-x64), checks a SHA-512 that zwinger pins for each version and arch (the registry's `dist.integrity` must name the same hash before the download starts, and the download must match it), writes only the expected binaries into `<app_data>/runtimes/<name>/<version>/` and mounts that dir at `/opt/zwinger/<name>`. A shield start mounts the runtimes that are installed then, so a runtime installed later needs a shield restart. The user can cancel a download; a stalled download fails after 60 s with no data. The app removes the work dirs of unfinished installs when it starts.

**Chat**: one conversation with an agent of a shield. Its id is unique per agent, so the agent kind is part of its identity. pi chats are pi session files in the app data dir (`shields/<id>/sessions`), mounted read-write with the rest of the agent state at `/opt/zwinger/state`. The guest can write these files, so the app reads them without following links. Claude Code and Codex chats are transcripts that the host writes (`chats/<shield>/<agent>/<id>.jsonl`, with the agent, the CLI session id, the model, the title and, for Claude Code, the guest cwd of the session), outside the guest-writable state, plus the CLI's own session state in `/opt/zwinger/state`. Claude Code keeps its sessions per cwd, so a Claude Code chat resumes in its saved cwd, also after a harness change. If that folder is gone, or an older chat has no saved cwd, the chat gets a notice and a new Claude Code session in the harness. Chats stay after a stop, so an old chat can be opened again. A shield delete removes them.

**Secret**: a named credential for a shield, such as `OPENAI_API_KEY`, with a list of exact hosts (no wildcards) and the request places where it is used: named header fields (such as `authorization`), query and body. Only the named header fields get the value, so a host that echoes other headers cannot show it to the agent. The agent sees only a placeholder (`$MSB_<NAME>$`) in the variable. The network proxy replaces the placeholder with the value only in requests to the secret's hosts, after a TLS identity check. A host must also be reachable under the network policy. The value is in the macOS Keychain (service `zwinger`, account `<shield-id>/<name>`), never in `shields.json`, and the UI can write it but not read it. At app start, Keychain values that no configured secret uses are deleted. While the shield runs, the value is also in the microsandbox run config of the VM. After a crash it can stay there until the next app start reaps the VM. A value change applies on the next shield start.

**App**: a saved, named, long-running command of a shield, such as a dev server: `name`, `command` (one shell line), `cwd` (`/workspace` or a folder below it or below a mount; the default is the harness) and `autostart`. It is in the shield config and has a stable id. Start runs `/bin/sh -lc <command>` in the shield's VM as a terminal that the app owns, not a view; the last 256 KiB of output stay, so its view can attach later. It is running, exited (with a code) or stopped. Stop and a shield stop end it. An autostart app starts after each shield start; a bad command shows only as an exit code. No port of an app is published to the host. An app edit applies at once, with no restart.

**Layout**: the map positions that the user dragged, per shield, by stable node id (`folder:<name>`, `mount:<guest>`, `host:<domain>`, ...). A node with no saved position takes its place from the auto layout. Reset layout clears the positions. Positions of nodes that no longer exist are dropped on the next save. A layout change needs no restart.

**Host agent**: an agent that is installed on the user's Mac and that shields reuse, instead of a separate copy per shield. A JS agent (pi, Gemini CLI) is mounted read-only from the host install. A native agent (Claude Code, Codex) uses one cached Linux build of the same version, mounted read-only into every shield. Its subscription login is proxy-injected (ADR 0002). Planned (M5c); today each agent runs from a pinned runtime.

**Agent profile**: the user's own configuration of a host agent (skills, instructions, settings, extensions, themes), mounted read-only into a shield. It never contains the login or the sessions of other projects. Planned (M5c).
