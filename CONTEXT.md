# zwinger domain

zwinger is a Mac app that runs AI coding agents in microVMs next to the user's own terminals. This glossary names its concepts; the code, the UI and the docs use these names.

## Code names

- **Session** is `Session` and `SessionView` in the code, `sessions.json` on disk, and "project" in the UI.
- **Cage** is `Cage` and `CageView` in the code and `cages.json` on disk. The UI shows the cage settings of a session on the session's page.
- **Terminal** is `Terminal`, `TerminalView` and `TerminalKind` (the process) and `TerminalRecord` (the saved record in `terminals`). The process commands keep their names (`open_session`, `attach_session`, `write_session`, ...).
- **Cage** and **VM** are both in the Rust `cage` module and its manager. VM state is `Status` in Rust and `CageStatus` in the frontend; `start_cage`, `stop_cage` and the event `cage-start-progress` start and stop a VM. Today each session has its own cage, with the same id, and one VM.
- `projects.json` is the store of older builds. The first start reads it once and converts it; the app never writes it.

## Organization

**Workspace**:
A named group of sessions in the sidebar. It is for organization only: it has no folder and no process. It can name a default cage for its sessions.
_Avoid_: group, folder. The guest path `/workspace` is a different thing.

**Session**:
One host folder on the Mac with its terminals, its pane layout and its tasks. Its default name is the basename of the folder. A session uses its own cage, the cage of its workspace, or no cage. The user creates, renames and deletes sessions; the config is in `sessions.json` in the app data folder, and the config of its cage in `cages.json`. Builds before #118 stored both in `projects.json`. When `sessions.json` or `cages.json` is missing, the start converts each project to one session and one cage with the project's id, writes `cages.json`, then `sessions.json`, and keeps `projects.json` unchanged. Builds before ADR 0005 stored the projects in `shields.json`: the conversion first copies that file to `projects.json` once, when `projects.json` is missing, and keeps the old file.
_Avoid_: project, shield

**Session folder**:
The host folder of a session. In a VM with one session it is mounted read-write at `/workspace`; in a VM with more sessions at `/workspace/<slug>`, with a slug fixed when the session is made (ADR 0007).
_Avoid_: project folder, shield folder

## Isolation

**Cage**:
A saved config for a sandbox: mounts, network policy, credentials, host agents, agent profiles and the setting "Agents run without permission prompts". It is not a process; a VM runs it. Nothing else from the host is visible in its VMs: no host env vars, no credentials, no host home.
_Avoid_: shield, cage profile, sandbox

**VM**:
A running microVM of a cage, the unit of isolation. By default all sessions of a cage share one VM; the user can start more VMs from the same cage (ADR 0006). A **VM start** boots it with the session folders, the mounts and the network policy of its cage; a **VM stop** ends it. The VM name is `zwinger-<VM key>`: the VM key of the shared VM is the cage id, so it did not change with the renames.
_Avoid_: shield, cage (for the process)

**Mount**:
An extra host folder that the user adds to a cage explicitly. It has an absolute guest path that does not overlap `/workspace`. It is read-only by default. The app stores the canonical path and the identity (device and inode) of each session folder and each mount. A start checks both at the claim, right before the boot and right after it; a mismatch refuses the start, or stops the VM that just booted. Two windows stay open: a swap and a swap back between the last check and the bind mount of the boot, and a swap before the first load after the upgrade that added the identities (that load takes the folders as they are then). A folder that is missing at that load has no identity: a start refuses it until the user confirms the folder.

**Network policy**:
The egress rules of a cage. All egress of a VM goes through its app proxy (ADR 0003); the VM can reach only the proxy port. The policy is one **default** (Block or Allow everything else), **Offline** (blocks all requests now and keeps the rules), and a list of **rules**: each names a service of the app's catalog (such as GitHub or npm, with its domains) or a host (`a.io`, or `*.a.io` for the domain and its subdomains, never a public suffix) and says Allow or Block. The proxy checks each request in this order: offline; the always-blocked addresses after it resolves the host on the Mac (this computer and the networks on its links, the LAN, loopback, shared and link-local ranges, cloud metadata; for a CONNECT before its answer) and the refresh hosts of the host logins; Block rules; Allow rules; the default. Block always beats Allow. A rule edit applies to the next request, with no restart. The proxy logs each request (method, host, path with query names only, status, sizes, time, decision, reason, credential names); a direct connection that the VM blocked shows as "direct connection blocked — this tool ignores the proxy". Ingress is always denied. Older configs migrate once: Public becomes default Allow and keeps its stored domains as Allow rules, List default Block with Allow rules, Deny the same and Offline.

**Credential**:
A named value that an Allow rule of a cage gives to its hosts, such as `GITHUB_TOKEN` on the GitHub rule. It goes to the exact host of a host rule, or to the credential hosts of a service (GitHub: `github.com`, `api.github.com`; a service wildcard only on a registrable domain). A wildcard host rule takes no credential: it can cover hosts of other owners. The proxy adds a credential only to HTTPS requests; a plain `http://` request goes out without it, and the log says `no credential: plain http`. The proxy refuses `TRACE` and `TRACK`, which echo the request. A credential on a Block rule is **inactive**: it stays, with its stored value, but the proxy adds it nowhere until the rule allows its host again. It is **set** (the proxy sets a header from a template such as `Bearer {secret}` or `{basic:x-access-token}`, also when the agent sends none) or **replace** (the proxy replaces the placeholder `$MSB_<NAME>$` only where the agent sent it: named header fields, query, body). The agent sees only the placeholder in the variable. Never give a credential to a host that echoes requests back (such as `httpbin.org`, `postman-echo.com` or an `echo.*` host): the UI warns. Rules can share a name, and with it one value. The value is in the **vault file** `<app data>/vault/credentials.json` (key `<cage id>/<name>`), never in `cages.json`, and the UI can write it but not read it; the UI shows a credential with no stored value as Not set. The file is versioned JSON with mode 0600 in a folder with mode 0700; the app refuses a wider mode or a symlink. Each change writes a temp file in the same folder, syncs it and renames it over the file, under one lock. Any process of the same macOS user can read the file. A value change applies to the next request. At app start, values in the file that no credential uses are deleted. There is no migration from the macOS Keychain of older versions: the app never reads or deletes those items, and the user enters the values again. The proxy terminates TLS with the app's own CA. The app makes a new CA in memory at each app start and never stores its key; each run logs its SHA-256 fingerprint. Each VM start replaces the zwinger block in the guest's system bundle with it, and `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` and `GIT_SSL_CAINFO` point at it. An image with no system bundle gets none, and the VM shows a notice. The M2 secrets of older configs became credentials for their hosts: on an Allow rule where the old policy reached the host (Public mode, or the allow list of List mode), else inactive on a Block rule.
_Avoid_: secret

**Start progress**:
The phases of a VM start: vault, prepare (with one profile phase per agent profile), proxy, boot, guest (the Node check, the host pi TUI probe, the Gemini probe, the login profile setup and the CA trust, each with its own timing), wrappers. The status of a starting VM names its phase, and the event `cage-start-progress` (`{ cageId, phase, elapsedMs }`) reports each phase change. The start logs one line with each phase's duration, and the running VM keeps them as its start timings (Settings tab, Last start). The guest checks run at once. Before the first start, the app stops `zwinger-*` VMs that an earlier app run left in the current runtime home, because they trust an old CA; a failed Node check fails the start, else their notices keep a fixed order. A host pi TUI probe that passed is cached in app data per pi version (read from its `package.json` at start), image and microsandbox version, and is not run again; a failed probe is not cached.

**Runtime home**:
The microsandbox home of zwinger, `~/.zwinger/microsandbox` (mode 0700), with the VM runtime (`msb`, `libkrunfw`), the VM database, the images and the VM sockets. It is short because each VM socket path (`<home>/run/sandboxes/<24 hex>/control.sock`) must be shorter than 104 bytes; a home that does not fit fails a system check. The start installs the runtime from the app binary when it is missing, damaged or of another version, but never replaces a runtime that `MSB_PATH` names. zwinger's own files (`sessions.json`, `cages.json`, preferences, agent runtimes) stay in the app data folder. The homes of earlier builds (`<app data>/microsandbox`, `~/.microsandbox`) are legacy homes: each start stops zwinger's VMs there, and Storage offers to remove zwinger's data from them.

## Terminals

**Terminal**:
One interactive process of a session, and its saved record (`terminals`: stable id and kind). Kinds: **host shell** (the default: the user's login shell on the Mac, unsandboxed, in the session folder; it needs no VM), **VM shell** (a login shell in the session's guest folder of the running VM; an explicit choice) and **agent terminal**. Each VM terminal gets `PATH` with `/opt/zwinger/bin` first, `TERM=xterm-256color` and `COLORTERM=truecolor`. A VM stop does not end a host shell; a session delete and the app exit do. The backend owns each terminal process, not a view: the last 1 MiB of its output stays, and a view attaches to it by id (also after a window reload), gets that output and the exit, and then new output. A later attach takes over; a detach leaves the process running. Output goes to the view as binary frames of up to 64 KiB, and the view acknowledges each frame. While a view has 8 frames that it did not acknowledge, the terminal stops reading the process, so the process waits. A view that acknowledges nothing for 5 s is detached. The tree shows all terminals of a session in one Terminals group, each with the icon of its kind. The list order is the tree order and is saved; a reorder or a new terminal needs no restart. A terminal with no live process is **dormant**: after a VM stop or an app restart it shows with no process, and Open starts a new process under the same id, in the same place. A VM start does not open dormant terminals. Only Close removes a terminal, and it ends its process.
_Avoid_: session (for a process), tab

**Agent terminal**:
A terminal that runs an agent's own CLI and TUI (Claude Code, Codex, pi, Gemini CLI) in the harness, else in the session's guest folder. zwinger has no chat UI of its own: the user sees the agent's interface with all its functions. "Continue last session" starts the CLI with its continue flag (`claude -c`, `codex resume --last`, `pi -c`, `gemini --resume latest`). It runs in a VM; in a session with no cage it runs on the Mac with a guard (ADR 0008).
_Avoid_: agent session, chat

**Pane layout**:
The split tree of a session's terminal view: each leaf shows one terminal, splits go right or down, and any kinds can sit side by side. It is saved per session and restored after a restart; a dormant terminal in it opens on click. A new split opens a host shell in the same folder. Closing a pane hides the terminal; only Close in the tree ends its process.

**Editor**:
An IDE on the Mac (Zed, VS Code, Cursor, ...) that the app finds in `/Applications`, `~/Applications` and `/Applications/Setapp`. The user turns editors on and picks a default in Settings or onboarding; a pick in a launcher also makes it the default. Open in editor opens a host folder in it (`open -a`): from a session, its folder; from a terminal, its current folder, else the session folder. A Mac shell's folder comes from macOS. A VM shell reports its folder with OSC 7 at each prompt, and the backend reads it from the output stream; a path below the session's guest folder or a mount maps to its host folder, any other path to the session folder.
_Avoid_: IDE (in names)

**Theme**:
A named set of overrides for motiv tokens (colors, radius, fonts, density) and a terminal ANSI palette, on a light or dark base. The app has built-in themes; user themes are JSON files in the app data `themes/` folder, made with Duplicate and edit on the Appearance page. App CSS uses tokens only, never raw colors. A terminal follows the app theme unless the terminal settings name a theme.

**Layout**:
The map positions that the user dragged, per session, by stable node id (`folder:<name>`, `mount:<guest>`, `host:<domain>`, ...). A node with no saved position takes its place from the auto layout. Reset layout clears the positions. Positions of nodes that no longer exist are dropped on the next save. A layout change needs no restart.
_Avoid_: pane layout (that is the split tree)

## Agents

**Agent**:
An AI coding CLI: pi, Claude Code, Codex or Gemini CLI. It runs as its own TUI in an agent terminal, or headless in a task run. One source in the app (`agent/launch.rs`) gives each agent its state env, its program and its flags. At each start the app writes one wrapper script per agent that the VM has (`claude`, `codex`, `pi`, `gemini`) into a host-only dir (`bin/<VM key>`), mounted read-only at `/opt/zwinger/bin`, and writes `/etc/profile.d/zwinger.sh` in the guest, so a login shell, whose `/etc/profile` resets `PATH`, also finds them. Each wrapper and headless command also sets the proxy and CA env itself, so an agent that clears its env keeps them. Claude Code gets `HOME=/opt/zwinger/state/claude` and `IS_SANDBOX=1` (the guest runs as root), Codex `CODEX_HOME=/opt/zwinger/state/codex`, pi `PI_CODING_AGENT_DIR=/opt/zwinger/state/agent` and its sessions in `/opt/zwinger/state/sessions`, Gemini CLI `HOME=/opt/zwinger/state/gemini`, so the host `~/.claude`, `~/.codex` and the others are never visible. The agent state is in `<app data>/shields/<VM key>`. The cage setting "Agents run without permission prompts" (on by default) adds `--dangerously-skip-permissions` (Claude Code), `--dangerously-bypass-approvals-and-sandbox` (Codex) or `--yolo` (Gemini CLI), unless the user gives a permission or approval flag, or a subcommand that starts no session (`claude mcp|config|doctor|update`, `codex login|logout|mcp`). That is acceptable only because the agent runs inside the VM: the VM is the sandbox, with only its mounts, its allowed hosts and placeholders for its credentials. When the setting is off, Codex still gets `--sandbox danger-full-access`: its own sandbox does not work in the VM. A change of the setting rewrites the wrappers of a running VM at once. An agent authenticates with credentials (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY` or `CODEX_API_KEY`, `GEMINI_API_KEY`), with a host login (see Host agent), or with its own `/login`, which needs Allow rules for the provider's login hosts. Such a guest login keeps the real token, with its refresh token, in the guest, where the agent can read it. A running VM looks for one at the start and every 10 s (by the shape of the fields only, never the values) and warns: 'Remove it' deletes the login file, 'Use my Mac login instead' opens the Host agents settings. Gemini CLI runs only as a host agent, from the entry point that detection reads from `bin.gemini` of its `package.json` (else `bundle/gemini.js`, then `dist/index.js`; it must stay inside the package). Each headless agent process of a task run runs in a small Node wrapper that puts it in its own process group, so a cancel or a stop kills the tool processes that the agent started, not only the agent.

**Runtime**:
The program of an agent, mounted read-only below `/opt/zwinger`; the VM needs no registry access. zwinger bundles pi (`/opt/zwinger/pi`). Claude Code and Codex are not bundled: the user installs them once, for all cages. The host downloads a pinned npm package for the host arch (linux-arm64 or linux-x64), checks a SHA-512 that zwinger pins for each version and arch (the registry's `dist.integrity` must name the same hash before the download starts, and the download must match it), writes only the expected binaries into `<app_data>/runtimes/<name>/<version>/` and mounts that dir at `/opt/zwinger/<name>`. A VM start mounts the runtimes that are installed then, so a runtime installed later needs a VM restart. The user can cancel a download; a stalled download fails after 60 s with no data. The app removes the work dirs of unfinished installs when it starts.

**Host agent**:
An agent that is installed on the user's Mac (Claude Code, Codex, pi, Gemini CLI) and that a cage reuses, instead of its own copy. The app finds them in their known install paths only (no login shell) at app start and on request, never in a loop. A cage turns one on per kind (`hostAgents`: kind, profile, login); the change applies on the next start. A JS agent (pi, Gemini CLI) is mounted read-only from the host package at `/opt/zwinger/host/<name>` and runs with the VM's node. If the host pi does not start its TUI in the VM (for example, a darwin-only native module), the bundled pi runs and the session shows a notice; Gemini CLI has no bundled copy, so it then shows an error. A native agent (Claude Code, Codex) uses the cached Linux build of the host's version (`runtimes/<name>/<version>/`, shared by all cages), else the pinned runtime. A version that zwinger does not pin is downloaded only after the user confirms it once; its check is then only the registry's `dist.integrity`. Its subscription login is a **host login**: Claude Code uses a `claude setup-token` token entered per cage and stored in the vault as `CLAUDE_CODE_OAUTH_TOKEN`, with its save date. The proxy injects it only into `authorization: Bearer {secret}` on an exact-host Allow rule for `api.anthropic.com`. The guest gets only the placeholder. A missing token prevents start; its estimated expiry is 365 days after save, with a warning in the last 30 days. Claude has no refresh host and does not block `console.anthropic.com` or `platform.claude.com`. Codex and pi use their login files on the Mac; Gemini CLI checks its cached token at `oauth2.googleapis.com/tokeninfo`, which the proxy answers when it carries the placeholder and no Block rule names the host. The rest of that host stays blocked. zwinger never writes host login files. The other agents get a guest login file built from an allow-list of fields: the real non-secret fields, an inert refresh token and a far expiry. The proxy puts the token into the `authorization` header of requests to the provider's exact host (ADR 0002). pi's Copilot login takes that host from the `proxy-ep` field of its token (an exact `api.<name>.githubcopilot.com`, else the individual host). For a host that is not individual, the guest's access is the token's non-secret claims up to `proxy-ep`, then the placeholder: pi reads the host there, and the proxy puts in the rest of the token, with its signature. The proxy blocks the refresh hosts of the login's provider before any rule; no credential can go to such a host. pi's Copilot login so blocks `api.github.com` (the GitHub API of `gh` and a `GITHUB_TOKEN`), and the session says so. For Codex, pi and Gemini, the proxy reads the host token per request and caches it until it expires, so a new login on the Mac applies with no restart; the session shows the expiry. An expired file login fails the start: the user opens the agent on the Mac once. Antigravity is detected but not supported.

**Agent profile**:
The user's own configuration of a host agent, opt-in per cage and agent. At each start the app updates a host-owned snapshot (`profiles/<VM key>/<agent>`) in place with an allow-list of entries of the agent's config dir (for example `~/.claude`: settings.json, CLAUDE.md, skills, commands, agents, plugins). The snapshot is mounted read-only at `/opt/zwinger/profile/<agent>`. A file is copied only if it is new or its size or mtime changed; a filtered file is made again and written only if its result changed; an entry that the source has no more, or that a rule now skips, is removed; a link in the snapshot is removed, not followed. After an error the snapshot is removed, so the next start copies all again. After the file limit, a whole folder is skipped and counts once. A link is copied as its target only if the target stays below the canonical top-level entry that the link is in (a top-level link must point below the config dir). Denied names (projects, sessions, history, `.credentials*`, `auth.json`, `oauth_creds.json` and others) are skipped at any depth, also through a link. Below `node_modules`, package folders keep their names (such as the `history` package), but files with denied names are skipped. The copy has a size limit, drops credential fields of settings files, drops `projects` and `mcp_servers` (host folders and host commands) from Codex's `config.toml` (a file that is not TOML is dropped), points Claude Code's plugin paths at the mount and drops each plugin `projectPath` outside `~/.claude`. Logins, history, sessions and projects of the agent are never copied. The agent's state home in the guest gets links into the mount in place of the same entries; the app replaces those entries without following links, as the guest can write them. A write of the agent to its profile fails (read-only). The map shows it as `profile (ro)`.
_Avoid_: cage profile (that is a cage)

## Tasks

**Task**:
A request that two agents of a session plan, build and review together: `title`, `request`, two agents of different kinds (pi, Claude Code, Codex), each with an optional model, `gates` (shell lines such as `pnpm build`) and `workdir` (the session's guest folder or a folder below it or below a mount). The first agent decides a tiebreak. It has a stable id and a `slug`, the folder name of its runs, which a rename does not change. A task edit needs no restart. A task needs a cage.

**Run**:
One execution of a task, with the duo stages: blind parallel plans, up to 2 exchange turns, a tiebreak by the first agent if they do not agree, the implementation, the gates, a cross review by the other agent, one revision if the verdict is `revise`, and blind parallel final reviews. `ship` is true only if both final reviewers set it. Each stage call is one headless process per agent (`claude -p`, `codex exec --json`, `pi -p --mode json`) with an idle and a hard timeout; a kill ends its whole process group. A reply with no JSON gets one retry. An agent that fails is degraded: a failed plan gives a walkover, a failed exchange leads to the tiebreak, a failed final review withholds `ship`. A degraded outcome is never shown as agreement. Read-only stages get the read-only flags of the CLI where it has them (Claude Code without its edit tools, pi with read tools only; Codex has none in the VM), and the run compares the git state of the workdir before and after: a change is a violation. Outside a git work tree no check is possible, and the run says so. The run never commits or pushes. The user can write a message, which every following stage prompt includes, pause after the current stage, resume, pick the implementer until the implementation starts, answer open questions (the run waits for them), and cancel. A VM stop cancels its runs; the manifest is written once, also when a cancel and a stop race. Resume of a run after an app restart is not supported.

**Round**:
The files of a run, in the shape of a duo round (`events.jsonl`, `turns/plan-*.json`, `turns/t<n>-*.json`, `tiebreak.json`, `implementation.json`, `gates.json`, `crossreview.json`, `revision.json`, `final-*.json`, `manifest.json`, `transcript.md`). The record is in host app data (`tasks/<session id>/<slug>/<run>/`), which the guest cannot write, so an implementer cannot change a verdict. A copy goes to `<session guest folder>/.zwinger/tasks/<slug>/<run>/` at each stage boundary, independent of the harness. The app never reads that copy back and writes it without following links. A run starts only if the copy can be written. Git snapshots and diffs cover the session guest folder and exclude the round copy.

**Message**:
One entry of a round, typed `{from, to, kind, body}` (kinds: plan, reply, tiebreak, implementation, gates, review, revision, final, user, answer, event). Agents do not talk directly: the run is the broker, and the next stage's prompt includes the messages. The shape lets an A2A bridge expose a round later.

**Room**:
The live view of a round: the stages, the messages, each agent's current position, the disagreements and concessions, the verdicts, and the degraded agents. One reader builds it from the round files, for in-app runs and for duo round folders that the user opens on the host ("Open round folder…"). It reads only regular files up to 8 MiB, without following links, and polls twice a second. A round folder from outside the app is read-only: the user cannot step in.
