# zwinger domain

**Shield**: the unit of isolation. One shield is one host folder, one microVM, its mounts and its network policy. The folder is mounted read-write at `/workspace` in the VM. Nothing else from the host is visible: no host env vars, no credentials, no host home.

**Mount**: an extra host folder that the user adds to a shield explicitly. It has an absolute guest path that does not overlap `/workspace`. It is read-only by default.

**Network policy**: egress is denied by default. The user adds allowed domains (the allow list); `*.example.com` allows subdomains. In allow-list mode DNS resolves only listed names. "Allow all" means the public internet only. The host machine, the LAN, loopback, link-local and cloud metadata addresses are blocked in every mode. Ingress is always denied. Mount and network changes apply on the next shield start.

**Session**: one interactive terminal inside a running shield's VM. Kinds: `shell` (a login shell in `/workspace`) and agent session. Each one gets `PATH` with `/opt/zwinger/bin` first, `TERM=xterm-256color` and `COLORTERM=truecolor`. There are no host (unsandboxed) sessions.

**Agent session**: a session that runs an agent's own CLI and TUI (Claude Code, Codex, pi, Gemini CLI) in the harness, else in `/workspace`. zwinger has no chat UI of its own: the user sees the agent's interface with all its functions. "Continue last session" starts the CLI with its continue flag (`claude -c`, `codex resume --last`, `pi -c`, `gemini --resume latest`). A live agent session keeps the shield busy, so a login renewal does not restart it.

**Agent**: an AI coding CLI that runs in a shield: pi, Claude Code, Codex or Gemini CLI. It runs as its own TUI in an agent session or a shield terminal, or headless in a task run. One source in the app (`agent/launch.rs`) gives each agent its state env, its program and its flags. At each start the app writes one wrapper script per agent that the VM has (`claude`, `codex`, `pi`, `gemini`) into a host-only dir (`bin/<shield>`), mounted read-only at `/opt/zwinger/bin`, and writes `/etc/profile.d/zwinger.sh` in the guest, so a login shell, whose `/etc/profile` resets `PATH`, also finds them. Claude Code gets `HOME=/opt/zwinger/state/claude` and `IS_SANDBOX=1` (the guest runs as root), Codex `CODEX_HOME=/opt/zwinger/state/codex`, pi `PI_CODING_AGENT_DIR=/opt/zwinger/state/agent` and its sessions in `/opt/zwinger/state/sessions`, Gemini CLI `HOME=/opt/zwinger/state/gemini`, so the host `~/.claude`, `~/.codex` and the others are never visible. The shield setting "Agents run without permission prompts" (on by default) adds `--dangerously-skip-permissions` (Claude Code), `--dangerously-bypass-approvals-and-sandbox` (Codex) or `--yolo` (Gemini CLI), unless the user gives a permission or approval flag, or a subcommand that starts no session (`claude mcp|config|doctor|update`, `codex login|logout|mcp`). That is acceptable only because the agent runs inside the shield: the shield is the sandbox, with only its mounts, its allowed hosts and placeholders for its secrets. When the setting is off, Codex still gets `--sandbox danger-full-access`: its own sandbox does not work in the VM. A change of the setting rewrites the wrappers of a running shield at once. An agent authenticates with secrets (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY` or `CODEX_API_KEY`, `GEMINI_API_KEY`), with a host login (see Host agent), or with its own `/login`, which needs the provider's login hosts on the allow list. Gemini CLI runs only as a host agent, from the entry point that detection reads from `bin.gemini` of its `package.json` (else `bundle/gemini.js`, then `dist/index.js`; it must stay inside the package). Each headless agent process of a task run runs in a small Node wrapper that puts it in its own process group, so a cancel or a stop kills the tool processes that the agent started, not only the agent.

**Runtime**: the program of an agent, mounted read-only below `/opt/zwinger`; the shield needs no registry access. zwinger bundles pi (`/opt/zwinger/pi`). Claude Code and Codex are not bundled: the user installs them once, for all shields. The host downloads a pinned npm package for the host arch (linux-arm64 or linux-x64), checks a SHA-512 that zwinger pins for each version and arch (the registry's `dist.integrity` must name the same hash before the download starts, and the download must match it), writes only the expected binaries into `<app_data>/runtimes/<name>/<version>/` and mounts that dir at `/opt/zwinger/<name>`. A shield start mounts the runtimes that are installed then, so a runtime installed later needs a shield restart. The user can cancel a download; a stalled download fails after 60 s with no data. The app removes the work dirs of unfinished installs when it starts.

**Secret**: a named credential for a shield, such as `OPENAI_API_KEY`, with a list of exact hosts (no wildcards) and the request places where it is used: named header fields (such as `authorization`), query and body. Only the named header fields get the value, so a host that echoes other headers cannot show it to the agent. The agent sees only a placeholder (`$MSB_<NAME>$`) in the variable. The network proxy replaces the placeholder with the value only in requests to the secret's hosts, after a TLS identity check. A host must also be reachable under the network policy. The value is in the macOS Keychain (service `zwinger`, account `<shield-id>/<name>`), never in `shields.json`, and the UI can write it but not read it. At app start, Keychain values that no configured secret uses are deleted. While the shield runs, the value is also in the microsandbox run config of the VM. After a crash it can stay there until the next app start reaps the VM. A value change applies on the next shield start. A host login (see Host agent) is a secret whose value comes from the Mac at each start: it has header fields only, the vault never holds it, and the user cannot edit it.

**App**: a saved, named, long-running command of a shield, such as a dev server: `name`, `command` (one shell line), `cwd` (`/workspace` or a folder below it or below a mount; the default is the harness) and `autostart`. It is in the shield config and has a stable id. Start runs `/bin/sh -lc <command>` in the shield's VM as a terminal that the app owns, not a view; the last 256 KiB of output stay, so its view can attach later. It is running, exited (with a code) or stopped. Stop and a shield stop end it. An autostart app starts after each shield start; a bad command shows only as an exit code. No port of an app is published to the host. An app edit applies at once, with no restart.

**Layout**: the map positions that the user dragged, per shield, by stable node id (`folder:<name>`, `mount:<guest>`, `host:<domain>`, ...). A node with no saved position takes its place from the auto layout. Reset layout clears the positions. Positions of nodes that no longer exist are dropped on the next save. A layout change needs no restart.

**Task**: a request that two agents of a shield plan, build and review together: `title`, `request`, two agents of different kinds (pi, Claude Code, Codex), each with an optional model, `gates` (shell lines such as `pnpm build`) and `workdir` (`/workspace` or a folder below it or below a mount). The first agent decides a tiebreak. It is in the shield config with a stable id and a `slug`, the folder name of its runs, which a rename does not change. A task edit needs no restart.

**Run**: one execution of a task, with the duo stages: blind parallel plans, up to 2 exchange turns, a tiebreak by the first agent if they do not agree, the implementation, the gates, a cross review by the other agent, one revision if the verdict is `revise`, and blind parallel final reviews. `ship` is true only if both final reviewers set it. Each stage call is one headless process per agent (`claude -p`, `codex exec --json`, `pi -p --mode json`) with an idle and a hard timeout; a kill ends its whole process group. A reply with no JSON gets one retry. An agent that fails is degraded: a failed plan gives a walkover, a failed exchange leads to the tiebreak, a failed final review withholds `ship`. A degraded outcome is never shown as agreement. Read-only stages get the read-only flags of the CLI where it has them (Claude Code without its edit tools, pi with read tools only; Codex has none in the VM), and the run compares the git state of the workdir before and after: a change is a violation. Outside a git work tree no check is possible, and the run says so. The run never commits or pushes. The user can write a message, which every following stage prompt includes, pause after the current stage, resume, pick the implementer until the implementation starts, answer open questions (the run waits for them), and cancel. A shield stop cancels its runs; the manifest is written once, also when a cancel and a stop race. Resume of a run after an app restart is not supported.

**Round**: the files of a run, in the shape of a duo round (`events.jsonl`, `turns/plan-*.json`, `turns/t<n>-*.json`, `tiebreak.json`, `implementation.json`, `gates.json`, `crossreview.json`, `revision.json`, `final-*.json`, `manifest.json`, `transcript.md`). The record is in host app data (`tasks/<shield>/<slug>/<run>/`), which the guest cannot write, so an implementer cannot change a verdict. A copy goes to `<harness>/.zwinger/tasks/<slug>/<run>/` at each stage boundary. The app never reads that copy back and writes it without following links. A run starts only if the copy can be written.

**Message**: one entry of a round, typed `{from, to, kind, body}` (kinds: plan, reply, tiebreak, implementation, gates, review, revision, final, user, answer, event). Agents do not talk directly: the run is the broker, and the next stage's prompt includes the messages. The shape lets an A2A bridge expose a round later.

**Room**: the live view of a round: the stages, the messages, each agent's current position, the disagreements and concessions, the verdicts, and the degraded agents. One reader builds it from the round files, for in-app runs and for duo round folders that the user opens on the host ("Open round folder…"). It reads only regular files up to 8 MiB, without following links, and polls twice a second. A round folder from outside the app is read-only: the user cannot step in.

**Host agent**: an agent that is installed on the user's Mac (Claude Code, Codex, pi, Gemini CLI) and that a shield reuses, instead of its own copy. The app finds them in their known install paths only (no login shell) at app start and on request, never in a loop. A shield turns one on per kind (`hostAgents`: kind, profile, login); the change applies on the next start. A JS agent (pi, Gemini CLI) is mounted read-only from the host package at `/opt/zwinger/host/<name>` and runs with the VM's node. If the host pi does not start its TUI in the VM (for example, a darwin-only native module), the bundled pi runs and the shield shows a notice; Gemini CLI has no bundled copy, so it then shows an error. A native agent (Claude Code, Codex) uses the cached Linux build of the host's version (`runtimes/<name>/<version>/`, shared by all shields), else the pinned runtime. A version that zwinger does not pin is downloaded only after the user confirms it once; its check is then only the registry's `dist.integrity`. Its subscription login is a **host login**: a secret whose value zwinger reads on the Mac at each shield start (Claude Code from the Keychain item `Claude Code-credentials`, macOS asks once to allow access; Codex and pi from their login files). Gemini CLI has no host login yet: it checks its cached token at `oauth2.googleapis.com`, which the proxy cannot answer (issue #16). zwinger never writes the host Keychain or host login files, and the vault never has the value. The agent gets a login with placeholders only (`CLAUDE_CODE_OAUTH_TOKEN`, or a guest login file built from an allow-list of fields: the real non-secret fields, an inert refresh token and a far expiry); the proxy puts the token into the `authorization` header of requests to the provider's exact host (ADR 0002). pi's Copilot login takes that host from the `proxy-ep` field of its token (an exact `api.<name>.githubcopilot.com`, else the individual host). For a host that is not individual, the guest's access is the token's non-secret claims up to `proxy-ep`, then the placeholder: pi reads the host there, and the proxy puts in the rest of the token, with its signature. The refresh hosts of the login's provider are denied in every network mode, also Public; such a host cannot also be on the allow list or a host of a user secret. pi's Copilot login so blocks `api.github.com` (the GitHub API of `gh` and a `GITHUB_TOKEN`), and the shield says so. A running VM keeps its token: the shield shows the expiry. From 10 minutes before it, the shield reads the login on the Mac again on a backoff (1 to 10 minutes) until the VM stops. If the Mac has no newer login, the shield tells the user to open the agent on the Mac once; a restart with the same token would not help. If it has one, the shield shows 'Restart to renew', and restarts by itself only if the user turned that on and no agent session, app or task run works in it. A login with no readable expiry is not renewed; the shield says so. An expired host login fails the start: the user opens the agent on the Mac once. Antigravity is detected but not supported.

**Agent profile**: the user's own configuration of a host agent, opt-in per shield and agent. At each start the app copies an allow-list of entries of the agent's config dir (for example `~/.claude`: settings.json, CLAUDE.md, skills, commands, agents, plugins) into a host-owned snapshot (`profiles/<shield>/<agent>`), mounted read-only at `/opt/zwinger/profile/<agent>`. A link is copied as its target only if the target stays below the canonical top-level entry that the link is in (a top-level link must point below the config dir). Denied names (projects, sessions, history, `.credentials*`, `auth.json`, `oauth_creds.json` and others) are skipped at any depth, also through a link. Below `node_modules`, package folders keep their names (such as the `history` package), but files with denied names are skipped. The copy has a size limit, drops credential fields of settings files, drops `projects` and `mcp_servers` (host folders and host commands) from Codex's `config.toml` (a file that is not TOML is dropped), points Claude Code's plugin paths at the mount and drops each plugin `projectPath` outside `~/.claude`. Logins, history, sessions and projects are never copied. The agent's state home in the guest gets links into the mount in place of the same entries; the app replaces those entries without following links, as the guest can write them. A write of the agent to its profile fails (read-only). The map shows it as `profile (ro)`.
